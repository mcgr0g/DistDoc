# System Patterns: Техническая архитектура и требования к реализации

## 1. Архитектурный стиль и требования к среде рантайма
Плагин спроектирован как расширение (User Defined Aggregate Function — UDAF) для распределенного SQL-движка **Trino 481+**. 
Система должна поддерживать выполнение на многоузловых кластерах, разделяя вычисления на фазы локального накопления (`Input`), 
межсетевого обмена (`Shuffle/Serialize`) и финального объединения (`Combine/Output`).

## 2. Основные технические ограничения и паттерны
Для обеспечения стабильности больших DWH-запросов и константного потребления памяти на уровне миллиардов строк, 
в реализации должны соблюдаться следующие паттерны:

### Паттерн 1: линейный стриминг (линейная сложность по памяти)
* **Требование:** Категорически запрещено строить полное DOM-дерево JSON-документа в оперативной памяти (никаких аллокаций тяжелых объектов на каждую строку).
* **Реализация:** Разбор должен выполняться строго через однонаправленный потоковый парсер (Streaming API) 
  с временной сложностью `O(N)` и пространственной сложностью по памяти `O(1)` относительно размера одной обрабатываемой строки.

### Паттерн 2: симметрия и изоляция рекурсивных стеков путей
* **Требование:** Построение путей JSONPath должно быть детерминированным и защищенным от побочных эффектов глубокой вложенности экранированных под-документов.
* **Реализация:** Управление иерархией полей должно осуществляться через ручной стек путей. 
  При обнаружении вложенного экранированного JSON-документа текущий стек путей должен изолированно копироваться и передаваться во внутренний рекурсивный контекст. 
  Под-документ не должен иметь физической возможности нарушить баланс токенов и структуру путей родительского документа.

### Паттерн 3: динамическая стратегия расширения аномалий (паттерн Стратегия)
* **Требование:** Ядро стриминг-парсера должно быть полностью абстрагировано от конкретных бизнес-правил dbt (правил валидации дат, регулярных выражений и т.д.).
* **Реализация:** Логика анализа массивов выносится в изолированный интерфейс-стратегию (`AnomalyDetector`). 
  Парсер по завершении обработки массива лишь поставляет неизменяемый снимок данных (DTO Context) в этот интерфейс.

### Паттерн 4: динамический маршалинг состояния (Open-Closed Serialization)
* **Требование:** Сетевой сериализатор состояний Trino кластера не должен изменяться или перекомпилироваться при добавлении новых пользовательских флагов аномалий в dbt-детектор.
* **Реализация:** Метод сериализации должен разделять служебные метаданные (`type`, `max_length`) и динамическую карту аномалий. 
  При десериализации из сети все неизвестные свойства JSON автоматически интерпретируются как булевы флаги аномалий и восстанавливаются в памяти рантайма.

### Паттерн 5: безопасность распределенного рантайма (Fault Tolerance)
* **Требование:** Ошибки синтаксиса JSON (битые строки), а также сетевые сбои при передаче пакетов 
  метаданных между воркерами Trino не должны приводить к аварийной остановке всего SQL-запроса (Query Failure).
* **Реализация:** Все критические фазы разбора и десериализации сетевых блоков памяти должны быть 
  защищены рантайм-перехватчиками. В случае сбоя маршалинга или парсинга система обязана подавить исключение и 
  вернуть пустое или частично сохраненное состояние схемы, гарантируя непрерывность выполнения процессов DWH.
