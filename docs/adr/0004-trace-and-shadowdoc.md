# 0004 Trace identifiers and ShadowDoc

Status: accepted
Date: 2026-09-10

## Context and Problem Statement
При работе с прод-данными политики компаний часто запрещают прямой доступ к БД
и передачу выборок агентам. Нужно: (1) уметь находить документы-виновники аномалий
и новых узлов jsonpath — трассировать идентификаторы строк в rx-data (`.rx.json`);
(2) интроспектировать прод-схему без установки плагина на прод — через shadow-кластер,
который «призывают» только в тяжёлых случаях.

Проблема трассировки: что считать идентификатором в неизвестных данных? Решения
пользователя: пресет — только системные id-поля (без business_key/doc_code/code), кастомные поля
передаются явно; `trace('field_name')` передаёт ИМЯ атрибута; без кавычек сформируется ссылка на 
колонку (в UDAF уходит её значение) рядом с интроспектируемым json полем, а это не входит в 
скоуп проекта так как анализу подлежит только 1 json поле; кластер называется `shadowdoc`, 
mise-задачи имеют префикс `sd-`.

## Decision
**Фаза 1 — trace_ids в плагине.**
UDAF `analyze_json_schema` получает перегрузку по числу аргументов
(прецедент `max_by(x,y)` / `max_by(x,y,n)` в core Trino): `analyze_json_schema(json, trace(...))`.
Scalar-функция `trace()` / `trace(v)` маркирует режим; пустой `trace()` включает пресет.
Конфигурация (лимит `max_ids`, длина id, ранжированный пресет, суффикс-правило) —
в TOML-ресурсе `app-config.toml` (секция `[trace]`), читается классом `TraceSettings`;
при ошибке чтения/парсинга — исключение. Пресет и суффикс могут быть переопределены
env-переменными `DISTDOC_TRACE_PRESET`/`DISTDOC_TRACE_SUFFIX` — заданная переменная
полностью заменяет значение из `[trace]`. Массив `trace_ids` (до `max_ids` элементов)
попадает в rx-data только для новых узлов jsonpath и путей с аномалиями; в обычном режиме
ключа в отчёте нет — контракт без трассировки не меняется. При распределённом merge
порядок id недетерминирован, лимит соблюдается.

**Фаза 2 — ShadowDoc (shadow-кластер `shadowdoc`).**
Прод-Trino подключается как read-only каталог `remote` через сторонний Apache-2.0
коннектор kkd927/trino2trino (встроенного Trino→Trino коннектора в открытом Trino нет).
Плагин DistDoc выполняется локально в shadow-контейнере — на прод он не устанавливается.
Аутентификация — параметры JDBC-драйвера: `connection-password` для LDAP/basic,
`accessToken` в URL для OAuth2 (значение подставляет пользователь в `REMOTE_TRINO_URL`).
Персистентность — переменная окружения: таблицы Trino всегда in-memory (Memory connector),
`SHADOW_PERSIST=true` дополнительно сохраняет копию rx-data в
`etc/shadowdoc/data/<REMOTE_TABLE>-<timestamp>.rx.json` (bind-mount, переживает `sd-dn`).
Mise-задачи `sd-up`/`sd-dn`/`sd-cli`/`sd-schema`; вершины DAG: `lc-demo` (lc-schema +
пост-остановка `lc-dn`), `sd-demo` (lc-load → sd-schema с пост-остановкой `lc-dn` и `sd-dn`),
`lc-verify` (test + оба прогона + `lc-dn`); `lc-schema` остаётся изолированной задачей.
`lc-up`/`sd-up` ждут healthcheck контейнера (`up -d --wait`).

## Consequences
- Трассируемость: по `trace_ids` инженер извлекает документ целиком, деперсонализирует
  и передаёт агенту; обычный контракт `.rx.json` и прод не затронуты.
- Прод безопасен: read-only каталог, плагин не ставится, политики доступа соблюдаются.
- Стенд зависит от GitHub-релиза коннектора (пин точного тега `trino-481-r2`);
  контрольные суммы не проверяются (HTTPS + пин тега; чексуммы — будущая reliability matrix).
- Keycloak-эмуляция локально не разворачивается: проверка цепочки OAuth2 делается
  на реальном контуре; в shadow-стенде аутентификация покрыта параметрами JDBC.
- Данные таблиц shadow переживают рестарт только как файлы в `./data`; полноценное
  персистентное хранилище таблиц (Delta/Iceberg) — отдельная отложенная задача.
